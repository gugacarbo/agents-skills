# Revisão da Skill `super-planning`

**Data:** 2026-07-09
**Escopo:** Skill inteira (SKILL.md, fases 01–08, prompts, templates, scripts, agents, docs, interfaces, dev/tests)
**Estilo:** Revisão crítica completa
**Suite de testes no momento da revisão:** RED (1 teste falhando — ver C4)

---

## Visão Geral

A skill tem uma arquitetura sólida: helper-path ativo (vendored vs `.super-planning/`), `super-plan.json` como single source of truth validado por script, gates de review em duas stages, capability adapter multiplataforma, compressão de contexto via file-based handoffs. Os problemas encontrados são **majoritariamente de consistência interna** (enum de status divergente entre schema/validator/SKILL.md, paths inconsistentes, idioma misto, órfãos de documentação) e de **sequenciamento Fase 5↔6** — não de arquitetura. Corrigir os CRÍTICOS deixa a skill executável de ponta a ponta.

## MÉDIOS (consistência, DX, robustez)

### SKILL.md (roteador)
- `reviewCadence` citado em "Shared Rules" mas nunca definido no SKILL.md (só na Fase 5). Enumerar valores ou linkar.
- "Decision Flow" ASCII não cobre o entry point `stats` nem o re-dispatch.
- `scripts/render-task-md.sh` e `summarize-all-tasks.sh` ausentes do "See Also".
- `user-invocable: true` no frontmatter — verificar se o loader da plataforma honra esse campo.

### Fase 1
- Step 2 ("Assess scope early") manda decompor em sub-projetos, mas não diz *para onde vai* essa decomposição (novo doc? múltiplas specs?). Faltam regras de output.
- Sem gate de erro/recuperação explícito se o usuário discorda na "Validate the direction".
- Não há flag de saída registrando que o visual companion foi usado.

### Fase 1.1 (visual companion)
- Colisão de namespace `.super-planning/` (companion brainstorm em `.super-planning/brainstorm/` + helper stack em `.super-planning/super-plan.sh` quando não-vendored). Documentar coexistência ou separar.
- `start-server.sh` assume `node` — dependência não declarada; sem fallback se ausente.
- `state_dir/events` lido "se presente" sem especificação de formato — o agente vai adivinhar.
- Sem gate de cleanup: `stop-server.sh` existe mas a fase **nunca instrui quando parar o servidor**. Risco de processo órfão.
- `start-server.sh` referencia `CODEX_CI` e `BRAINSTORM_*` — leakage de outra plataforma.

### Fase 2
- Step 4 saltou para 5 na lista "Pre-Write Approval Gate" (numeração markdown: 1, 2, 3, **5**).
- "Check Workspace Documentation Patterns" manda seguir convenções existentes, mas a regra "plan MUST use the same number" assume estritamente `docs/specs/NNNN-...`. Sem fallback de naming para repos que divergem.
- Spec self-review é manual, sem artefato gravado de "passou".
- "Optional Spec Document Review Subagent" entra em tensão com o spec-template que chama o decisions file de "optional" (ver M-templates).

### Fase 3
- "Execution Handoff" re-promptea paralelo vs sequencial depois que a decisão já foi tomada no decision flow do SKILL.md. Tardio e contraditório.
- "Target 2–5 minutes of subagent work" — unidade estranha para LLM (depende do modelo/repo). Melhor medir em passos ou deliverables testáveis.
- "File Structure" com Owner Task no plan-file vs `super-plan.json` — não há regra de "single source of truth", risco de drift.
- Plan template não tem seção para as tarefas (só wrapper) — explicitar que steps vivem no JSON, não no markdown.

### Fase 4
- Paths forward-reference obrigatórios no momento da criação (`reportFile`, `reviewPackage`, `progressLog`, `logTaskScript` exigidos não-vazios), mas os arquivos só existem na Fase 6. Não há nota de que são paths planejados — o agente pode achar que precisa criar os dirs.
- `worktree.path` default `../$PLAN_ID-worktree` — path fora do repo; sem discovery de suporte a worktree antes do `init`. Default `enabled=true` arriscado.
- `reviewCadence` default `per_task` no `init`, mas a Fase 4 exige perguntar ao usuário. Se o agente esquecer, fica `per_task` silenciosamente.
- `--set` em paths aninhadas (`tasks[Task-A-1].status`) documentado no usage mas sem exemplo na Fase 4.
- `request_user_input` (nome de tool) citado em 3+ lugares — parece inventado; confirmar API real do opencode (`question`).

### Fase 5
- "Scope Violation Detection" abre brecha: "infrastructure files like `package.json` or lockfiles are acceptable" sem qualificar. Um implementer poderia justificar tocar qualquer "infra" file.
- "Branch name: `NNNN-<feature-name>`" + branches por task (`NNNN-feature/Task-A-1`) em paralelo com worktree — esquema não registrado no `super-plan.json` nem validado.
- "Worktree isolation for parallel mode" recomenda `isolation: "worktree"` — parâmetro de dispatch específico de plataforma; não é genérico. Vale caveat.
- `materialize-task-logger` referenciado na Fase 5 mas a ação é "later in Phase 6" — redação confusa.
- `worker-prompt-template.md`: `Working Directory` placeholder não trata o caso worktree (cwd diferente por subagent).
- `worker-prompt-template.md`: "Do not read the rest of the plan" — não distingue "plan file" de "spec file" (a spec é referenciada por `source.spec` e provavelmente deveria ser permitida).
- `implementer-guidance.md` duplica `worker-prompt-template.md` em logging/report/status. Sem frase clarificando se são complementares ou se um substitui o outro.

### Fase 6
- `Minor` severity → "Record in progress ledger" — mas o ledger é gerado do `super-plan.json` + logs; **não há campo de findings no schema**. Instrução sem destino estruturado.
- Review package generation é descrita na Fase 5 e na Fase 6 — sobreposição de responsabilidade. Definir ownership único.
- `code-reviewer.md` "Project-Specific Customization" hardcoded (MANY SMALL FILES, RLS, AI integration, cache fallback) — leakage (ver A6).
- `code-reviewer.md` "Run a test only when reading the code raises a specific doubt" — mas o reviewer é read-only; rodar teste pode mutar (snapshot updates, codegen). Vale "run read-only test commands only".
- `file:line` em findings — o reviewer só tem o diff, não o arquivo completo; line numbers são do diff hunk, não do arquivo final. Especificar.

### Fase 7
- `spec-compliance-auditor.md` não lê `super-plan.json` — só a spec. Mas o plan/tasks têm `requirementsChecklist` com `coveredByTasks` que acelerariam o audit. Hoje o auditor redescobre o mapeamento.
- `spec-compliance-auditor.md` sem "Compressed Output Format" — para um audit de branch inteiro, o output pode ser enorme.
- Sem menção ao ledger final nem a marcar `status: completed` no root do JSON.
- File Map mandado produzir no Step 0 mas não listado no Output Format (Step 4).

### Fase 8 (reference)
- Diagrama de transição de status (linhas 79-84) inclui `cancelled` e mostra `ready_for_review → cancelled` (estranho — normalmente cancela-se de `pending`/`in_progress`).
- "Integration with Other Skills" desatualizada: `brainstorming` listado como "external companion" mas o SKILL.md Scope diz que foi absorvida pela Fase 1; `plan-with-subagents` com nome errado (a skill se chama `super-planning`).
- Error Recovery "default máximo 3 attempts" — mas `tryCount` no schema é só `minimum: 1`, sem `maximum`. Não há validação de limite.
- "Narration Discipline" (uma linha entre tool calls) entra em conflito com o modo conversacional de conduzir a skill — vale note de que se aplica ao *modo de execução de planos*.
- Investigator output format definido inline sem template nem agent — formato solto que se perde.

### `docs/workflows.md`
- Diagrama "Ciclo de Vida da Tarefa" **omite `reviewing`** como estado, embora o schema e a Fase 5/6 o usem.
- Diagrama de Dispatch Paralelo mostra "Review each task immediately as it finishes" para `per_task` — reforça o flag operacional A4.
- Idioma PT (ver A5).

### `docs/AGENT-DECISION-FLOW.md`
- Phase 4 flowchart tem lógica invertida (linhas 128-130): `"Need per-task directories or progress.log now?"` → `|Yes| I["No: defer task artifacts to Phase 6"]`. O "No:" prefix no label do ramo Yes é contraintuitivo.
- Status Lifecycle (linhas 249-261) inclui `cancelled` mas **omite `reviewing`** e a transição `ready_for_review → reviewing`.

### Scripts
- `render-progress-ledger.sh`: inclui `reviewing`+`cancelled` no status_map (consistente com validator, inconsistente com schema). Emojis ⏳🔄🔎🔍🔁❌✅⚪ — renderização frágil em CLI sem emoji-font. `resolve_workspace_root` heuristic frágil se `--task-directory` custom.
- `summarize-all-tasks.sh`: `STATUS_MAP` omite `reviewing` (diverge do render-progress-ledger). `find ... | sort` sem quoting — quebra em paths com espaços. Emojis. Python 3.10+ (ver A10).
- `render-task-md.sh`: header `## Task Task-A-1:` (duplicação feia — testado, mas vale `## Task-A-1:`).
- `super-plan.sh`: validator não checa unicidade de `task.id`/`requirement.id`. `parse_path` sem tratamento de escape (id contendo `]` quebra — risco baixo, ids controlados). `select_child` mensagens de erro pobres ("'field'").
- `log-task.sh`: aceita `completed` de qualquer chamador — sem guard de "só orchestrator". Se o ledger confiar no log, há bypass do gate de review.
- `visual-companion/start-server.sh`: contrato JSON do `server.cjs` não verificado (só `grep "server-started" | head -1`). `SESSION_ID="$$-$(date +%s)"` pode colidir. Sem teste para o companion.

### Templates
- `spec-template.md`: `builds-on` chama o decisions file de "optional" — contradiz "must always save" (Fase 1 step 8, Fase 2 step 3). `implemented-by` sem contrato de formato. Verification block "fill in at close" — sem ponto na Fase 7 que o demande.
- `decisions-template.md`: `Open Questions` duplica spec template sem regra de migração (decisions carrega todas? spec só herda não-resolvidas?).

### Interfaces
- `super-plan.schema.json`: `$schema` no payload preenchido com path de disco absoluto pelo `init` (não URI estável). Quebra semântica de `$schema` e vira lixo se o repo muda de máquina. Sem campo de `createdAt`/`updatedAt` para auditoria.

### `dev/tests.sh`
- Não valida o schema `.schema.json` em si — só o validator Python embutido. Se validator e schema divergem (e divergem em `cancelled`/`reviewing`), nenhum teste pega.
- `test_update_accepts_cancelled_task_status` asserta que `cancelled` é aceito — passa só porque valida contra o validator, **não contra o schema**. Falso positivo de consistência.
- Cobertura ausente: `append-task` (documentado); `--set` em `requirementsChecklist[REQ-001].status` (path por id em outro array); `log-task.sh` modo `log` (só `materialize-task-logger` é testado); visual companion scripts (zero cobertura).
- `python3 -c` inline assume python3 — não declarado como dep.
- `dev/README.md` com path hardcoded `/home/gustavo/.agents/skills` — específico do ambiente, quebra portabilidade.

### Cross-cutting de executabilidade
- **Dependências não declaradas em lugar nenhum:** `python3` (todos os scripts), `node` (visual companion), `flock` (log-task), `git` (review package, auditor).
- **Floor de Python não fixado:** scripts usam desde syntax 3.7 até 3.10+. Padronizar e declarar.
- **POSIX vs Bash:** `super-plan.sh`, `render-progress-ledger.sh`, `summarize-all-tasks.sh`, `render-task-md.sh` são `#!/usr/bin/env sh` (POSIX, conforme convenção). `log-task.sh` e `start-server.sh` são `#!/usr/bin/env bash`. Decidir exceção ou converter.

## Recomendações Prioritárias

1. **Desbloquear testes (C4):** gerar `progress.log` nos fixtures de exemplo — caminho mais rápido para a suite voltar ao verde e validar o resto.
2. **Unificar o enum de status (C2):** definir `pending | in_progress | ready_for_review | reviewing | needs_fix | blocked | completed | cancelled` em **todos** os níveis (task, requirement, plan) no schema, validator, SKILL.md e diagramas. Adicionar um teste que valide schema-vs-validator agreement (rodar `jsonschema.validate` contra o `.schema.json`).
3. **Fix do handoff de logging (C3):** mover materialização do dir+wrapper para a Fase 5 antes do dispatch — resolve o gap e simplifica a fronteira Fase 5↔6.
4. **Decidir `tryCount` vs `maxTries` (C5 + A10):** adicionar `maxTries` ao schema, documentar `tryCount` como "tentativa atual", corrigir `summarize-all-tasks.sh`.
5. **Padronizar idioma e remover leakage de projeto (A5, A6):** traduzir `docs/` para inglês (ou tudo para PT — mas o resto é EN); limpar "Project-Specific Customization" e exemplos hardcoded dos agents.
6. **Declarar dependências:** lista em SKILL.md (python3 ≥3.10, node opcional para companion, git, flock em Linux) + fallback/aviso quando ausente.
7. **Documentar ou remover órfãos:** `append-task` (C1), `render-task-md.sh` (A12), `spec-document-reviewer-prompt.md` (A11).
