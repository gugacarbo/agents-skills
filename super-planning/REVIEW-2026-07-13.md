# Revisão completa da skill `super-planning`

**Data:** 2026-07-13  
**Escopo:** router, fases, prompts, agents, templates, schema, scripts, documentação, testes e evals  
**Resultado geral:** arquitetura forte, porém ainda sem garantias mecânicas suficientes para ser considerada independente do agente/modelo.

## Resumo executivo

A `super-planning` possui uma base conceitual acima da média:

- roteamento explícito e extensível por fase;
- semântica forward-only preservada para `/super-planning <phase>`;
- handoffs baseados em arquivos para reduzir pressão de contexto;
- `super-plan.json` como registry estruturado;
- ledger regenerado a partir do estado persistido;
- review packages baseados em `baseCommit` e merge-base;
- profiles `quick`, `general` e `deep` com capability fallback;
- review por task e auditoria final da branch.

O principal problema não é falta de instrução. Algumas instruções centrais ainda existem somente em prosa, enquanto os helpers aceitam operações que deveriam ser impossíveis. Também existem exemplos documentados que não satisfazem a própria CLI/schema.

### Avaliação por área

| Área | Avaliação |
| --- | --- |
| Arquitetura do workflow | Forte |
| Roteamento por fases | Claro e extensível |
| Handoffs e controle de contexto | Muito bom |
| Scripts e ledger | Funcionais no happy path |
| Consistência docs/runtime | Problemática em pontos críticos |
| Guardrails mecânicos | Insuficientes |
| Portabilidade | Parcial |
| Avaliação entre modelos | Não demonstrada |

## Bloqueadores

### C1. A Fase 4 documenta comandos de `init` que a CLI rejeita

Os exemplos em [`phases/04-decompose.md`](phases/04-decompose.md) omitem:

- `--worktree-enabled`
- `--execution-mode`
- `--review-cadence`

Entretanto, [`scripts/super-plan.sh`](scripts/super-plan.sh) exige os três argumentos antes de criar o skeleton.

Reprodução:

```text
{"error": true, "message": "Missing required argument for init: --plan-id, --feature-name, --spec, --plan, --output, --worktree-enabled, --execution-mode, --review-cadence", "exit_code": 1}
```

Além disso, a fase diz para confirmar profiles e review cadence depois do `init`, embora a CLI já exija parte dessas decisões durante o `init`.

**Correção sugerida:**

1. Mover as decisões de execution mode, worktree e cadence para antes do `init`; ou
2. Permitir um skeleton explicitamente incompleto e impedir dispatch até sua finalização.

Os exemplos de documentação devem ser executados pela suíte para impedir novo drift.

### C2. O exemplo canônico de task não satisfaz o schema

O JSON de exemplo da Fase 4:

- usa `phase`, enquanto o schema exige `layer`;
- não contém `maxTries`;
- define `tryCount: 3`, embora o campo aparente representar a tentativa atual.

Reprodução:

```text
{"error": true, "message": "tasks[0] is missing required keys: maxTries, layer", "exit_code": 1}
```

**Correção sugerida:**

```json
{
  "tryCount": 1,
  "maxTries": 3,
  "layer": "foundation"
}
```

Também é recomendável gerar esse exemplo a partir da mesma fixture usada nos testes.

### C3. O state machine não é aplicado pelo helper

A skill declara que tasks só podem chegar a `completed` depois de review limpo. Porém, o helper aceita diretamente:

```text
task: pending -> completed
task.baseCommit: pending
plan: pending -> completed
```

Essa transição foi reproduzida com sucesso. O validator confere o enum, mas não valida a transição anterior nem exige evidência de review para `completed`.

Isso compromete o objetivo de criar guardrails independentes do modelo: um agente pode ignorar o processo e a ferramenta aceita o resultado.

**Correção sugerida:**

- criar `transition-task`, `complete-task` e `complete-plan`;
- validar pares `from -> to`;
- exigir `baseCommit`, report, review package e evento de review antes de completar;
- bloquear conclusão quando dependências não estiverem completas;
- bloquear conclusão do plano enquanto existirem tasks não resolvidas;
- restringir ou remover `--set ...status=` genérico.

### C4. `append-task --validate-only` não valida tasks

O subcomando apenas verifica se a entrada é um array e retorna `valid: true`. Ele não executa `validate_json` nem valida cada task contra o schema.

Reprodução:

```json
[{"bogus": true}]
```

Resultado:

```json
{"valid": true, "count": 1}
```

**Correção sugerida:** inserir as tasks em uma cópia temporária do registry e executar exatamente o mesmo pipeline de validação usado no write real.

### C5. Proveniência e update estão quebrados no modo não-vendorizado

Quando `super-plan.sh` é copiado para `.super-planning/`, `reference` resolve o Git root e o remote do projeto-alvo, não da skill original.

Reprodução em um projeto temporário:

```text
repository = https://github.com/example/product-app.git
commit = unknown
skillPath = <projeto-alvo>/.super-planning
```

Como consequência, `super-update.sh` tenta clonar o remote do aplicativo e espera encontrar nele uma pasta `super-planning/`.

**Correção sugerida:**

- gerar a referência a partir da instalação original;
- persistir repository/ref/commit da skill;
- fazer `super-update.sh` usar `super-planning-reference.json` por padrão;
- permitir override explícito apenas quando necessário;
- pinar o `$schema` ao commit registrado, em vez de `main`.

### C6. O modo não-vendorizado não copia todos os helpers prometidos

O router de `stats` afirma que `.super-planning/summarize-all-tasks.sh` é copiado pela Fase 4. O bootstrap documentado não copia esse arquivo.

`render-task-md.sh` também é usado na Fase 5 sem um active-helper resolution claro no modo não-vendorizado.

**Correção sugerida:** criar um único comando `bootstrap` orientado por um manifest de helpers. Evitar listas de `cp` duplicadas em Markdown.

## Correções importantes

### A1. A Fase 6 exige um evento que o logger rejeita

A Fase 6 manda registrar Minor findings como evento `info`. `log-task.sh` aceita somente:

```text
started | ready_for_review | failed | blocked | completed
```

O smoke test com `--event info` falhou.

**Correção sugerida:** adicionar `info` ao contrato completo ou criar um campo estruturado `reviewFindings` no registry. Um campo estruturado é preferível para auditoria e filtros.

### A2. O visual companion possui problemas de lifecycle

O default de `start-server.sh` força foreground incondicionalmente. Em um shell convencional, o comando não retorna enquanto o servidor estiver vivo, embora a fase espere capturar o JSON e continuar a interação.

No modo `--background`, o servidor inicia e para corretamente, mas imprime três erros:

```text
local: can only be used in a function
```

Isso ocorre porque `server_line`, `server_port` e `health_result` são declarados com `local` fora de uma função.

**Correção sugerida:**

- background como default portátil;
- foreground somente quando solicitado ou identificado por capability;
- remover `local` no escopo global;
- adicionar teste start -> health -> stop;
- garantir stdout contendo apenas o JSON contratual.

### A3. Há drift entre fontes autoritativas

Exemplos atuais:

- Fase 3 e schema usam `layer`; Fase 4 e alguns diagrams ainda usam `phase`;
- Fase 5 materializa logger e `progress.log`, mas `SKILL.md`, Phase 8 e decision flow ainda atribuem parte disso à Fase 6;
- a lista de status da Fase 4 omite `reviewing`;
- o decision flow ainda mostra artefatos sendo adiados para Phase 6;
- `render-task-md.sh` não inicia o artifact com o marker obrigatório `Process: super-planning`.

**Correção sugerida:** adicionar contract tests que comparem schema, exemplos, lifecycle, campos e ownership de artefatos entre arquivos.

### A4. O teste chamado `schema_validator_agreement` não prova agreement completo

O teste atual:

- valida apenas um registry mínimo contra o JSON Schema;
- compara apenas o enum de status do plano;
- não compara required fields, additional properties, task fields, requirement fields ou invariantes do validator customizado.

Assim, schema e validator podem divergir enquanto o teste continua verde.

**Correção sugerida:** montar uma matriz de payloads válidos e inválidos e exigir o mesmo resultado do JSON Schema e do validator runtime.

Idealmente, usar o JSON Schema como única fonte e adicionar validações procedurais apenas para invariantes que o schema não consegue expressar.

### A5. A validação de distribuição rejeita o frontmatter

`skill-master/scripts/quick_validate.py` rejeita `user-invocable`.

**Correção sugerida:**

- adicionar formalmente o campo ao schema do validator, se ele for parte do formato suportado; ou
- mover a informação para `metadata`.

Não deixar a skill depender de um campo que a própria toolchain considera inesperado.

### A6. Dependências declaradas não correspondem ao runtime

`SKILL.md` declara Python >= 3.8, mas `super-plan.sh` usa `set[str]`, que requer Python 3.9 em runtime.

Além disso, `log-task.sh` é Bash, embora as convenções do projeto definam runtime scripts POSIX.

**Correção sugerida:**

- trocar `set[str]` por `Set[str]` importado de `typing`; ou elevar o floor para Python 3.9;
- converter o logger core para POSIX; ou documentar Bash como dependência e exceção oficial.

### A7. A integração final possui dependência externa implícita

Phase 7 exige `commit-changes` por path relativo. Isso funciona neste bundle, mas não necessariamente quando `super-planning` é distribuída isoladamente.

**Correção sugerida:** declarar a dependência formalmente e fornecer fallback de commit convencional quando a skill não estiver instalada.

## Lacuna de avaliação comportamental

Os evals atuais cobrem somente três cenários ligados a TDD e Phase 2. Eles não cobrem o valor central da skill: seguir o fluxo sob pressão, em diferentes modelos e plataformas.

### Cenários mínimos recomendados

1. Deadline pressionando para pular brainstorm ou aprovação.
2. Usuário/autoridade pedindo implementação direta em `main`.
3. Task concluída sendo redespachada após compactação de contexto.
4. Dispatch paralelo com ownership conflitante.
5. Entrada direta em fase sem os pré-requisitos necessários.
6. `reviewCadence=final_only`.
7. Spec alterada durante implementação.
8. Plataforma sem subagents.
9. Plataforma sem model selection explícita.
10. Plataforma sem worktrees.
11. Bootstrap não-vendorizado.
12. Tarefa trivial que não deve ativar a skill.
13. Invocação implícita sem `/super-planning`.
14. Recuperação após contexto compactado.
15. Cada comando da toolbox usado isoladamente.

### Método recomendado

- snapshot da versão atual como baseline;
- with-skill e baseline executados em pares;
- ao menos cinco fresh-context samples para guardrails disciplinares;
- dois ou mais modelos/profiles;
- assertions sobre transcript, arquivos, branches, registry e logs;
- captura de rationalizations usadas para pular gates;
- revisão humana dos prompts antes da execução;
- benchmark de pass rate, tokens, tempo e variância.

Sem essa evidência, a skill pode ser chamada de bem testada no runtime determinístico, mas não de verificada entre agentes/modelos.

## Evolução recomendada da toolbox

Preservar a semântica atual dos phase routes:

```text
/super-planning plan
```

continua significando “comece na Phase 3 e siga adiante”.

Adicionar um namespace separado para capacidades isoladas:

```text
/super-planning tool doctor
/super-planning tool bootstrap
/super-planning tool validate
/super-planning tool transition
/super-planning tool render-task
/super-planning tool review-package
/super-planning tool stats
```

### `doctor`

O comando deveria verificar:

- Python, Bash, Node e Git;
- branch atual;
- suporte a worktrees;
- versão e proveniência dos helpers;
- schema ativo;
- presença de artifacts obrigatórios;
- capabilities de subagents e model selection;
- integridade do registry;
- tarefas em estado impossível.

Isso reduz a quantidade de detecção que hoje depende da interpretação do agente.

## Conclusão

A arquitetura da `super-planning` é boa e o fluxo possui decisões maduras. O próximo salto de qualidade não virá de adicionar mais instruções, mas de transformar as instruções críticas em invariantes rejeitadas mecanicamente pelos helpers.

O objetivo de funcionar consistentemente entre agentes e modelos será defensável quando houver, simultaneamente:

1. documentação executável e alinhada ao schema;
2. state machine aplicada pela CLI;
3. bootstrap/provenance portátil;
4. evals comportamentais pareados sob pressão.
