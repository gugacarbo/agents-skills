# Portable watchdogs and Codex adapter implementation plan

## Summary

**Goal:** add a generic watchdog contract to `super-planning`, then implement
the Codex adapter with a continuation heartbeat and a read-only status heartbeat
in the same thread.

**Scope:** materialize per-provider watchdog configuration and prompts below a
target repository's `.super-planning/watchdogs/`; extend the portable registry
policy; add generic provider contract/template and Codex-only artifacts; wire
Phase 4, 5, and 7 lifecycle instructions; test and publish the skill.

**Out of scope:** implementing Cursor, OpenCode, CI, cron, systemd, or launchd
adapters; committing host/thread IDs; changing the active realtime-dashboard
feature.

**Success signal:** an opted-in plan can select a valid provider profile; the
target repository receives deterministic config/prompt artifacts; Codex creates
two same-thread heartbeats without a status chat; continuation obeys normal
lifecycle gates; status is read-only; all roles pause or disable safely.

## Context and design

The skill already has a portable task registry, generated ledger, and per-task
reports/logs, but no watcher contract. Source skill templates must remain
maintainable and versioned; target-repository runtime configuration must be
materialized under `.super-planning/` so a plan can change cadence without
committing host-specific identifiers.

**Architecture:**

1. `super-plan.json` gets an optional `continuation` selector with `enabled`,
   `provider`, `watchdogProfile`, and lifecycle `status`.
2. A new materializer writes
   `.super-planning/watchdogs/codex-watchdogs.json` plus independent prompt
   copies in `.super-planning/watchdogs/prompts/`.
3. `platforms/continuation/contract.md` and `template.md` define the generic
   extension boundary. `codex.md` and its JSON template implement the first
   provider only.
4. Phase 5 reads the selected profile and reconciles two Codex thread
   heartbeats. Phase 7 disables every active role at terminal states.
5. Local `.super-planning/continuations/<plan-id>.json` records host IDs per
   role and stays ignored. It is never copied into versioned plan data.

**Codex roles:**

| Role | Default cadence | Behavior |
| --- | --- | --- |
| `continuation` | 2 minutes | Resume only the next safe unfinished lifecycle action. |
| `status` | 15 minutes | Read artifacts and print a compact report in the same thread. |

The `test` profile keeps continuation at 2 minutes and sets `status` to 30
seconds. Same-thread status can interrupt active work; it is therefore
explicitly read-only and opt-in. A standalone cron is intentionally excluded
because it creates separate chats.

**Execution mode:** sequential. Schema/helper work, source templates, phase
guidance, and evaluation artifacts overlap in the same skill surface.

**Global constraints:**

- Watchdogs are explicit opt-in and disabled by default.
- Materialized provider config and independent prompts use the deterministic
  `.super-planning/watchdogs/` path; host IDs, credentials, and transcripts do
  not enter versioned artifacts.
- A `status` role attached to a Codex thread never edits files, task state,
  registry state, or automations.
- Never redispatch completed tasks or bypass dependency, worktree, review, or
  human-decision gates.
- Pause all roles for a human block; disable all roles for completed/cancelled
  plans.
- Preserve pre-existing realtime-dashboard and super-planning changes.
- TDD applies to behavior-changing schema/helper/lifecycle code according to
  `docs/context/testing-anti-patterns.md`.

## Risks and handoff

| Risk | Mitigation |
| --- | --- |
| Same-thread status interrupts work | Explicit opt-in, read-only prompt, documented trade-off, and test profile. |
| Duplicate roles | One local record per plan/provider/role plus reconciliation before creation. |
| Missing/invalid generated config | Materializer is idempotent; Phase 5 validates profile before host calls. |
| Host API drift | Isolate mechanics in `codex.md`; preserve generic core contract. |
| Dirty current checkout | Preserve all unrelated changes; do not dispatch implementation until the user authorizes the recorded dirty-tree exception. |

**Registry handoff:** retain `docs/jobs/0002-codex-continuation-watchdog/` and
rewrite its pending task definitions through `super-plan.sh` only after this
revised plan is approved. Existing choices remain: direct `main` execution
with explicit user authorization, sequential batches, per-batch independent
review, `gpt-5.6-terra`/medium for deep work, and `gpt-5.6-luna`/medium for all
other roles where the platform supports those selections.
