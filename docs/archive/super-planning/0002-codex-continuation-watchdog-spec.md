# Resume and observe super-planning execution through portable watchdogs

> Shared conventions: `super-plan.json` is the versioned source of truth;
> the active helper path owns registry mutations; `.super-planning/` holds
> generated, repository-local runtime artifacts and private host state. This
> feature does not change the active realtime-dashboard plan.

## Objective

Allow an executing super-planning plan to opt into portable watchdog roles.
The initial Codex adapter implements two heartbeats in the same thread: one
resumes safe unfinished work, and one reports current execution status. The
core contract and template must allow future platform adapters without changing
the lifecycle rules; only Codex is implemented in this release.

## Flow

1. Phase 4 materializes provider watchdog configuration under the target
   repository's `.super-planning/watchdogs/` directory. Codex uses the fixed
   default path `.super-planning/watchdogs/codex-watchdogs.json` and copies
   prompt files to `.super-planning/watchdogs/prompts/`.
2. During Phase 5, before the first implementation wave, the orchestrator asks
   whether to enable watchdogs for the selected plan and which configured
   profile to use.
3. If declined, the registry remains disabled and no host automation or local
   continuation record is created.
4. If accepted, the orchestrator records the portable provider/profile policy,
   validates the materialized provider config, loads the selected adapter, and
   creates or updates each configured watchdog role.
5. Codex attaches both roles to the current thread. `continuation` resumes only
   safe unfinished work; `status` is read-only and prints an evidenced status
   report in that same thread.
6. The adapter stores host identifiers only in local continuation metadata. A
   same-thread status heartbeat can interrupt active work; it must not be
   replaced by a standalone cron merely to avoid interruption, because crons
   create separate chats.
7. A human block pauses every active role. Completed or cancelled plans disable
   every active role, including during Phase 7 cleanup.

## Contract

### Portable registry policy

`continuation` is an optional top-level `super-plan.json` object. Omission is
backwards-compatible and means disabled. It selects a provider and profile;
cadence and prompt details are provider configuration, not host identifiers.

```json
{
  "continuation": {
    "enabled": false,
    "provider": "codex",
    "watchdogProfile": "default",
    "status": "disabled"
  }
}
```

- `enabled` is required when `continuation` exists.
- `provider` is a stable adapter identifier. The first schema supports only
  `codex`; future adapters extend the enum with their matching documents.
- `watchdogProfile` defaults to `default`; it must name a profile in the
  materialized provider config.
- `status` is one of `disabled`, `active`, or `paused`.
- No automation ID, thread ID, credential, host URL, or transcript may appear
  in versioned plan data.

### Generic adapter and provider-config contract

Each adapter lives in `platforms/continuation/<provider>/` and starts from
`platforms/continuation/template.md`. Every adapter must define:

1. its provider identifier and required host capability;
2. named watchdog roles, creation/update/pause/disable operations, and
   idempotency/concurrency safeguards;
3. the fixed `.super-planning/watchdogs/<provider>-watchdogs.json` default
   path, profile schema, and prompt-file materialization rules;
4. independent prompt files and their terminal/blocking behavior;
5. local metadata path/schema; and
6. verification cases and platform-specific non-goals.

Core phases select adapters only by provider identifier; they must not embed
provider API parameters or host identifiers. Adding a future provider consists
of its adapter, config template, prompts, and schema enum value; no core
lifecycle duplication is allowed.

### Materialized Codex configuration

Phase 4 writes `.super-planning/watchdogs/codex-watchdogs.json` and its
referenced prompt files. The file is configurable and has these shipped
profiles:

| Profile | Continuation | Status |
| --- | --- | --- |
| `default` | thread heartbeat every 2 minutes | read-only thread heartbeat every 15 minutes |
| `test` | thread heartbeat every 2 minutes | read-only thread heartbeat every 30 seconds |

The generated config references independent files below
`.super-planning/watchdogs/prompts/`. The source skill ships templates, not a
live automation file. Changing intervals or profile selection changes the
desired configuration; only the adapter reconciles that configuration with the
Codex host automation API.

### Codex adapter

The initial `codex` adapter creates two heartbeats attached to the current
thread, never standalone workspace crons:

- `continuation` reads plan/task artifacts and resumes only the next safe,
  unfinished lifecycle action;
- `status` reads plan/task artifacts and Git state, then reports plan status,
  batch/task counts, latest progress, blockers, active execution evidence, and
  the next safe action. It makes no files, lifecycle, dispatch, or automation
  mutation.

The adapter stores `planId`, `provider`, `watchdogRole`, `threadId`,
`automationId`, `status`, and timestamps only in:

```
.super-planning/continuations/<plan-id>.json
```

The continuation prompt MUST preserve dependency, worktree, review, completed
task, and human-decision gates. The status prompt MUST state that it can
interrupt active work, remain read-only, and never be silently converted to a
cron that opens a separate chat.

## Lifecycle ownership

Phase 4 owns default provider-config and prompt materialization. Phase 5 owns
consent, adapter/profile resolution, host creation/update, and local metadata.
Phase 7 owns terminal cleanup. Adapters never change registry status directly;
all plan/task changes continue through the active `super-plan.sh` helper.

## Edge cases

| # | WHEN trigger | the system MUST response |
| --- | --- | --- |
| 1 | a legacy registry has no `continuation` | treat watchdogs as disabled and validate successfully. |
| 2 | a user declines watchdogs | create no host automation or local continuation record. |
| 3 | an enabled plan already has a role record | update/reuse that role instead of creating a duplicate. |
| 4 | config/profile is missing or invalid | create no automation and report the exact materialized path and error. |
| 5 | local metadata is missing or stale | recreate only after confirming enabled, non-terminal policy and valid profile. |
| 6 | a heartbeat sees completed/cancelled | disable every role and mark local records inactive. |
| 7 | a heartbeat needs a human decision or sees blocked | pause every role and report the exact blocker. |
| 8 | host creation/update fails | leave no false active local state and report the actionable host failure. |
| 9 | status fires during active work | report only evidenced state in the same thread; make no mutation or duplicate dispatch. |
| 10 | a provider config uses a standalone cron for same-thread status | reject it and require a thread-bound status watchdog. |
| 11 | a future provider is added | add its adapter/config/prompt template and schema enum without core lifecycle edits. |
