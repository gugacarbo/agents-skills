# Decisions for Codex continuation watchdog

## Summary

Add a portable, opt-in watchdog capability to `super-planning`. The core
defines reusable provider contracts and configuration materialization; Codex
is the only initial adapter and schedules two heartbeats in the active thread:
one to resume safe unfinished work and one to report execution status.

## Chosen Approach

Define a platform-neutral watchdog contract and template, then add only the
Codex adapter now. Phase 4 materializes provider configuration beneath the
target repository's `.super-planning/watchdogs/` directory. The default Codex
file is `.super-planning/watchdogs/codex-watchdogs.json`; its independent
prompt files live in `.super-planning/watchdogs/prompts/`. Private host and
thread identifiers remain in the Git-ignored
`.super-planning/continuations/<plan-id>.json` record. Future platforms add an
adapter and provider config template without changing core Phase 5 or Phase 7
lifecycle rules.

## Requirements Shaping These Decisions

- Enable the watchdog only through an explicit Phase 5 user decision.
- Default the feature to disabled. The `default` profile uses a 2-minute
  continuation interval and a 15-minute status interval; a `test` profile may
  use a 30-second status interval.
- Make profile and intervals configurable through the materialized provider
  configuration, with prompts stored as independent files.
- Create at most one active automation per watchdog role, plan, and host.
- Resume from `super-plan.json`, `progress-ledger.md`, task reports, and
  progress logs; never rely solely on chat history.
- Never redispatch completed tasks or bypass lifecycle, dependency, worktree,
  review, or human-decision gates.
- Pause the watchdog when the plan is blocked on a human decision; disable it
  when the plan becomes `completed` or `cancelled`.
- Keep Codex status in the same thread; it is read-only but may interrupt an
  active execution when its heartbeat fires. Do not use a standalone status
  cron that creates separate chats.
- Provide a provider template and contract for a later Cursor, OpenCode, or
  other-host adapter.

## Constraints

- The first implementation supports Codex only and uses its thread-heartbeat
  automation capability; the generic template does not imply implementation
  for Cursor, OpenCode, CI, or OS schedulers.
- Creating, changing, or disabling an automation is an external state change
  and must be performed only through the host automation API.
- Do not store automation IDs, thread IDs, secrets, or user-specific host data
  in versioned plan artifacts.
- Preserve the active realtime-dashboard plan and its unrelated uncommitted
  source and distribution changes.
- Extend the existing schema and helper flow compatibly so prior registries
  without continuation data remain valid.

## Assumptions

- Codex heartbeats attached to the active thread are the appropriate way to
  preserve conversation continuity. A test confirmed that a heartbeat can
  interrupt active agent work, so the status watchdog must be explicitly
  read-only and opt-in.
- The active host can create, update, and delete heartbeats through the
  automation capability when Phase 5 runs.
- `.super-planning/` is already ignored by this repository and is suitable for
  local continuation records in non-vendored target repositories.

## Non-Goals

- Implementing Cursor, OpenCode, CI, cron, systemd, or launchd adapters.
- Building a generic cross-platform scheduler runtime.
- Automatically resolving product or implementation decisions that require a
  user response.
- Persisting, exporting, or replaying full chat transcripts.

## Risks and Tradeoffs

- A scheduled wakeup can cause duplicate work unless the adapter checks plan
  state and local ownership before dispatch; the resume prompt must make those
  checks mandatory.
- Platform automation APIs may evolve independently; the adapter isolates that
  coupling while the core contract remains portable.
- Local metadata can be lost when a checkout moves machines; the plan remains
  recoverable manually from versioned artifacts, but the host automation must
  be recreated.

## Alternatives Considered

| Option | Why it was not chosen |
| ------ | --------------------- |
| Put Codex API details directly in Phase 5 | It would make future platforms modify core lifecycle guidance and mix portable policy with host mechanics. |
| Use a repository shell scheduler | It cannot reliably resume the active Codex conversation and would introduce machine-specific runtime management. |
| Use a standalone status cron | It creates independent chats instead of reporting in the active conversation. |
| Commit automation and thread IDs into `super-plan.json` | They are private, host-specific, and invalid for other users or machines. |

## Open Questions

- None. The user approved the modular Codex-first direction and default cadence.
