# Decisions for realtime jobs dashboard

> This file captures the decisions produced during Phase 1 brainstorming.
> It is always saved before writing the spec in Phase 2.

## Summary

Add a browser-based, real-time, read-only dashboard to the `super-planning`
skill so users on the local network can observe plan, task, requirement, and
progress-event state without reading generated JSON, JSONL, or Markdown files.

## Chosen Approach

Create a dedicated jobs server and dashboard instead of extending the Phase 1
visual companion. Expose it through a new start script and the discoverable
`/super-planning tool dashboard` route. The server reads registries and task
logs directly, pushes changes to connected browsers, and never mutates job
state.

## Requirements Shaping These Decisions

- Scan every `super-plan.json` below `docs/jobs` by default.
- Treat `super-plan.json` and task `progress.log` files as primary inputs;
  `progress-ledger.md` remains a derived artifact.
- Show a cross-plan overview with plan/task status, progress, requirements, and
  task event details.
- Refresh connected browsers in real time when registry or progress-log data
  changes.
- Bind to the LAN by default and require a generated session token for every
  browser session.
- Keep the first version strictly read-only.
- Make the capability available in vendored and bootstrapped helper layouts.
- Require focused TDD with observed RED/GREEN evidence for behavior-changing
  server, authentication, snapshot, and live-update work.

## Constraints

- Preserve the existing status lifecycle and helper mutation guardrails.
- Do not couple the operational dashboard lifecycle to temporary brainstorm
  companion sessions.
- Keep runtime dependencies aligned with the skill's existing supported
  environment and avoid adding a package-install step.
- Preserve current uncommitted work in `super-planning`, including overlapping
  documentation and visual-companion changes.
- Keep shell entry points compatible with the repository conventions.

## Assumptions

- `docs/jobs` is the default jobs root, with an override available for unusual
  repository layouts.
- LAN clients can reach the selected host and port directly; tunnel, TLS, DNS,
  and internet deployment are outside the first version.
- A generated bearer-style URL token is sufficient for LAN access in this
  first version.
- A dashboard covering all plans, with drill-down into individual tasks, is
  more useful than launching one server per plan.

## Non-Goals

- Transitioning plan, task, or requirement states from the browser.
- Dispatching, cancelling, retrying, or messaging subagents.
- Editing `super-plan.json`, `progress.log`, reports, or review packages.
- Providing a hosted public service, TLS termination, or tunnel management.
- Replacing `progress-ledger.md` or `summarize-all-tasks.sh`.
- Reusing the dashboard as a Phase 1 mockup/brainstorm companion.

## Risks and Tradeoffs

- LAN-default binding increases exposure, so authenticated requests and safe
  token handling are mandatory rather than optional.
- Files can be observed while another process is replacing or appending them;
  the dashboard must retain the last valid snapshot and surface transient read
  errors without crashing.
- Recursive filesystem watching behaves differently across operating systems;
  correctness must not depend on a platform-specific watch feature.
- A dedicated server adds files and bootstrap/update surface area, but keeps
  brainstorm and job-monitoring responsibilities isolated.

## Alternatives Considered

| Option                                                   | Why it was not chosen                                                                                         |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Extend the visual-companion server with a jobs mode      | It couples a persistent operational dashboard to temporary Phase 1 screen/session behavior.                   |
| Serve a page that periodically polls generated summaries | It is simpler but provides weaker real-time behavior and repeatedly reparses state even when nothing changed. |
