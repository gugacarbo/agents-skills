# Observe super-planning jobs through an authenticated real-time web dashboard

> Shared conventions: follow the repository `AGENTS.md`, prefix workspace
> commands with `rtk`, keep shell entry points compatible with the established
> script conventions, and preserve the lifecycle defined by `super-plan.json`.
> The decisions consumed by this spec are recorded in
> [`0001_realtime_jobs_dashboard_decisions.md`](../spec-decisions/0001_realtime_jobs_dashboard_decisions.md).

## Objective

Allow a user on the local network to start one authenticated, read-only web
dashboard and observe the current state of every super-planning plan, task,
requirement, and task progress stream under a project without manually opening
JSON, JSONL, or generated Markdown artifacts.

## Flow

1. From a target project, the user runs the vendored or bootstrapped dashboard
   helper, directly or through `/super-planning tool dashboard`.
2. The start command resolves the project and jobs roots, binds to `0.0.0.0` by
   default, generates or reuses an owner-only session token, starts the server,
   verifies an authenticated health response, and prints machine-readable JSON
   containing the complete URL and lifecycle metadata.
3. The user opens the complete URL, including `?key=...`, from a device that can
   reach the host. The server validates the token, sets an HttpOnly,
   SameSite=Strict session cookie, and redirects to the token-free root URL.
4. The dashboard loads an authenticated initial snapshot covering every valid
   `super-plan.json` below the jobs root and the associated task progress logs.
5. The overview shows aggregate counts and one plan card or row per registry.
   The user can filter by plan/task text or lifecycle status and open a plan to
   inspect tasks, requirements, dependencies, retry counts, latest events, and
   recent progress events.
6. The server checks the relevant registry and progress-log file signatures at
   most once per second by default. When a signature changes, it rebuilds the
   snapshot and sends it to authenticated connected browsers through a
   WebSocket. Browsers update without a page reload.
7. If a changed file is temporarily invalid or unreadable, the server keeps the
   last valid data, adds a visible warning identifying the affected relative
   path, and retries on the next scan. Once valid data returns, the warning is
   removed and clients receive the recovered snapshot.
8. The user stops the server with the same helper's stop operation or by ending
   foreground mode. Shutdown closes sockets, stops scanning, and removes live
   PID metadata without modifying anything below the jobs root.

## Contract

### Helper interface

The skill provides `scripts/job-dashboard/serve-jobs.sh` and exposes it through
`/super-planning tool dashboard`.

```text
serve-jobs.sh [--project-dir <path>] [--base-dir <path>]
              [--host <bind-host>] [--url-host <display-host>]
              [--port <port>] [--refresh-ms <milliseconds>]
              [--foreground] [--open]
serve-jobs.sh --stop [--project-dir <path>]
```

- `--project-dir` defaults to the current working directory.
- `--base-dir` defaults to `<project-dir>/docs/jobs` and may be absolute or
  project-relative.
- `--host` defaults to `0.0.0.0`; `--url-host` controls only the hostname in the
  printed URL and never changes the bind interface.
- `--port` defaults to an available ephemeral port. An explicitly requested
  occupied or invalid port fails without silently selecting another port.
- `--refresh-ms` defaults to `1000`, has a documented minimum of `250`, and
  controls server-side file-signature scans rather than browser polling.
- Detached mode is the default so the command can return connection metadata;
  `--foreground` transfers lifecycle ownership to the current terminal.
- `--open` opens the complete authenticated URL on the server host when a
  supported opener exists; inability to open a browser is a warning, not a
  startup failure.
- `--stop` is idempotent and refuses to signal a PID unless per-start instance
  metadata proves it belongs to this dashboard.
- Invalid arguments, missing Node.js, an absent jobs root, startup failure, or
  failed authenticated health checks return non-zero with an actionable error.

Successful detached startup prints exactly one JSON object to stdout:

```json
{
  "type": "job-dashboard-started",
  "pid": 12345,
  "port": 52341,
  "url": "http://workstation.local:52341/?key=<session-token>",
  "project_dir": "/absolute/project",
  "base_dir": "/absolute/project/docs/jobs",
  "state_dir": "/absolute/project/.super-planning/job-dashboard"
}
```

The concrete values vary per environment. Diagnostics and warnings go to
stderr so stdout remains parseable.

### Runtime and state

- The implementation uses Node.js 18 or newer and built-in modules only; it
  adds no package-install step or runtime dependency.
- Dashboard runtime metadata lives under
  `<project-dir>/.super-planning/job-dashboard/` and is owner-only where the
  operating system supports permissions.
- At most one dashboard instance is active per project runtime directory.
  Re-running the start command for a healthy instance returns that instance's
  current connection JSON instead of launching a duplicate.
- The session token is generated from cryptographically secure random bytes,
  is never written to the jobs tree, and is not printed in server logs.
- The server may read `super-plan.json`, task `progress.log`, and task
  `report.md` files needed by the established summary contract. It MUST NOT
  write, rename, delete, lock, or transition any file below the jobs root.
- The dashboard aggregation builds on `summarize-all-tasks.sh --json` or a
  shared equivalent extracted from it; terminal summary behavior remains
  backward compatible and aggregation semantics must not drift between CLI and
  dashboard output.

### Authentication and network behavior

- The LAN bind default is intentional; every dashboard HTML, snapshot API, and
  WebSocket request requires the session token or authenticated session cookie.
- The initial `?key=` request exchanges a valid token for an HttpOnly,
  SameSite=Strict cookie and redirects so the token does not remain in the
  address bar.
- Missing or invalid credentials return `403` without revealing registry data.
- WebSocket upgrades require both valid credentials and a same-origin `Origin`
  matching the request host. Invalid upgrades are rejected before a socket is
  registered.
- Responses set restrictive content-security, framing, MIME-sniffing, referrer,
  and same-origin resource headers. User-controlled registry and log text is
  rendered as text, never injected as executable HTML.
- `/healthz` is used by the start helper and requires valid credentials. It
  reports process health without returning job content.

### Snapshot and update behavior

Each snapshot has a stable envelope:

```json
{
  "type": "job-snapshot",
  "version": 1,
  "generatedAt": "2026-07-13T12:00:00Z",
  "totalPlans": 1,
  "grandTotal": {
    "totalTasks": 3,
    "completedTasks": 1,
    "completionPercent": 33.3
  },
  "plans": [],
  "warnings": []
}
```

- Plan/task/requirement status values preserve the canonical lifecycle strings
  without inventing dashboard-only states.
- Plan entries include the established CLI JSON summary fields. Task entries
  additionally expose recent valid progress events in chronological order so
  the detail view does not need filesystem access.
- The server retains at most the latest 200 valid progress events per task in a
  snapshot; `eventCount` continues to report the full valid-event count.
- Blank and malformed JSONL lines are skipped and represented by a warning;
  one bad line does not discard other valid events.
- Snapshots use project-relative display paths and do not expose files outside
  the canonical jobs root.
- The server emits an initial snapshot immediately after an authenticated
  socket connects. Later snapshots are emitted only when job data or warnings
  change, not on every scan tick.
- Multiple connected browsers receive the same immutable snapshot and cannot
  submit commands or state mutations through HTTP or WebSocket messages.

### Dashboard presentation

- The initial view shows total plans, task completion, requirement completion,
  and counts for every lifecycle status represented in the snapshot.
- Each plan exposes its feature name, plan status, completion percentage,
  status breakdown, and warning indicator.
- Plan detail exposes tasks, dependencies, batch/layer, retry counts,
  requirements coverage, last event, report summary when available, and the
  recent event timeline.
- Text and status filters operate locally in the browser and do not alter the
  server snapshot.
- The page indicates connection state (`connecting`, `live`, or
  `disconnected`), the last successful update time, and snapshot warnings.
- The layout remains usable on current desktop and mobile browsers without an
  external CSS or JavaScript CDN.

### Distribution and documentation

- Vendored files live under `super-planning/scripts/job-dashboard/`.
- `bootstrap.sh` copies the complete dashboard manifest into
  `.super-planning/job-dashboard/` for non-vendored target repositories.
- `super-update.sh` updates the same files without deleting unrelated runtime
  state.
- `doctor.sh --dashboard` checks Node.js and every dashboard manifest file.
- `SKILL.md` is authoritative for the `tool dashboard` route; `README.md`, the
  dependency table, Phase 4 bootstrap manifest, and relevant reference docs
  remain aligned.

## Edge cases

| # | WHEN trigger | the system MUST response |
| --- | --- | --- |
| 1 | the jobs root exists but contains no registries | serve an authenticated empty dashboard with zero totals and keep watching for the first registry |
| 2 | the configured jobs root does not exist at startup | fail startup with a non-zero exit and identify the missing path |
| 3 | a registry becomes malformed during an atomic or partial write | retain its last valid plan snapshot, show a warning, and retry without terminating the server |
| 4 | a newly discovered registry is malformed before any valid snapshot exists | omit that plan, show a warning for its relative path, and continue serving other plans |
| 5 | a progress log contains blank or malformed JSONL entries | keep all valid events, count only valid events, cap returned recent events, and show a warning |
| 6 | a registry or task directory is removed | remove it from the next valid snapshot without retaining stale plan or task data |
| 7 | the same job content is scanned without change | send no redundant WebSocket snapshot |
| 8 | a browser connects after changes occurred | send the latest complete snapshot immediately after authentication |
| 9 | a request or socket upgrade lacks valid credentials | return or close with an authorization failure and reveal no job data |
| 10 | a socket has valid credentials but a cross-origin Origin | reject the upgrade before registering the client |
| 11 | an explicit port is unavailable | fail startup and preserve any already-running unrelated process |
| 12 | the recorded PID is stale or belongs to another command | refuse to signal it, clear only stale dashboard metadata, and report `stale_pid` |
| 13 | one browser disconnects unexpectedly | remove only that client and keep the server and other clients running |
| 14 | the active helper layout is bootstrapped rather than vendored | resolve sibling dashboard and summary helpers without assuming the source skill directory exists |
| 15 | registry or log text contains HTML or script markup | display the literal text without executing markup |
| 16 | the server is stopped | close listeners and sockets and remove live PID metadata without modifying jobs or persisted token data |

## Test Strategy

- **Mode:** TDD for behavior changes, with observed RED before implementation
  and GREEN after the minimum change for each behavior slice.
- **Guidance file:** `docs/context/testing-anti-patterns.md`
- **Runner and commands:** Bash integration tests in
  `skills/super-planning/dev/tests.sh`, Node syntax checks, Bash syntax checks, and the
  repository gitignore integration test shown in the Definition of Done.
- **Fixtures:** temporary project roots containing realistic minimal
  `super-plan.json`, `progress.log`, and report files; tests interact with a real
  local server process and network socket rather than mocking the server under
  test.

| ID | Behavior | Test level | Expected evidence |
| --- | --- | --- | --- |
| T1 | startup defaults, JSON stdout contract, authenticated health, idempotent restart, and safe stop | integration | focused test first fails because the helper/server is absent, then passes with verified process cleanup |
| T2 | valid token bootstrap succeeds while missing/invalid tokens and invalid socket origins fail | integration/security | RED unauthorized/security assertions followed by GREEN HTTP and WebSocket checks |
| T3 | multiple registries aggregate into the documented snapshot and empty roots return zero totals | integration | RED snapshot assertions followed by GREEN exact plan/task/requirement totals |
| T4 | registry or progress-log changes produce one new socket snapshot without browser polling | integration | RED timeout before implementation followed by GREEN update within 2.5 seconds |
| T5 | malformed registry writes preserve the last valid snapshot and recover after valid replacement | integration | RED recovery test followed by GREEN warning, retention, and recovery assertions |
| T6 | malformed JSONL lines are skipped, warned, counted correctly, and recent events cap at 200 | unit/integration | RED boundary fixture followed by GREEN count/order/cap assertions |
| T7 | dangerous text is escaped and no jobs-root mutation endpoint or socket command exists | integration/security | RED injection/read-only assertions followed by GREEN literal rendering and rejected commands |
| T8 | bootstrap, updater, doctor, router, docs, and dependency declarations include the dashboard manifest | integration/static | RED manifest/reference assertions followed by GREEN complete distribution coverage |
| T9 | vendored and flat bootstrapped layouts resolve their active helpers correctly | integration | RED layout fixtures followed by GREEN startup and snapshot checks in both layouts |

- **Edge and error scenarios:** missing jobs root, explicit occupied port,
  stale/reused PID, malformed registry, malformed JSONL, removed plan, dropped
  client, cross-origin socket, missing Node.js, and browser opener failure.
- **Legacy coverage:** existing summarizer terminal and JSON tests, visual
  companion lifecycle coverage, helper bootstrap/update coverage, and the full
  super-planning suite must remain green. The job dashboard does not replace or
  relax visual companion coverage.
- **TDD exceptions:** documentation-only wording and static generated headers do
  not require RED/GREEN evidence, but their consistency assertions must pass in
  the integration suite.

## Human review

- Open the printed authenticated URL from a second device on the same LAN and
  confirm it loads without exposing the token after the redirect.
- Confirm plan overview, task drill-down, filters, warnings, and event timeline
  remain readable at desktop and narrow mobile widths.
- While the page is open, transition a fixture job through the existing CLI
  helper and confirm the visible state changes without a manual refresh.
- Confirm browser back/forward and reconnection behavior feel understandable;
  automated tests verify state, but not perceived clarity.
